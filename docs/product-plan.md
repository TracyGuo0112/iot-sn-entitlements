# IOT-SN 权益查询：Demo 与后续规划

## 已确认范围

- 面向客户查询，客户手动输入 appkey 后查看对应数据；本次全部使用模拟数据。
- appkey 是应用租户边界，同一 appkey 下 SN 唯一且只能领取一次；SN 不要求跨 appkey 全局唯一。
- 权益信息包括权益名称、激活状态、起止时间，以及关联订单、退款记录。
- 原订单列表中的“退款成功”表示真实资金退款，与导入触发的退权益分别展示。
- 提供 SN 查询、筛选、导入批次及逐台明细查询、筛选结果导出。
- 本次支持上传 Excel / CSV 清单发起批量查询；不提供 SN 导入、发放、重置权益、退款等写入操作，不接入生产接口。

## 业务口径

导入实际执行“SN 白名单幂等写入 + 退货补领”，需要保留每个输入 SN 的处理结果：

| 导入前情况 | 处理动作 | 批次明细结果 |
| --- | --- | --- |
| 新 SN | 新增白名单，并按规则初始化权益 | 新增成功 |
| 已导入、尚未领取 | 保留已有记录 | 已存在，跳过 |
| 已领取 | 退权益、恢复一次领取资格，并扣减对应商品 ID 的额度 | 退权益成功 |
| 校验失败或业务处理失败 | 返回具体原因，不伪装为成功 | 处理失败 |
| 尚无最终结果 | 等待处理结果 | 处理中 |

“退权益”是退货补领中的权益处理，不等同于资金退款。页面使用“退权益 / 资格重置”描述该动作；真实退款单独展示，不从重置结果推断。

同一 appkey 下，每个 SN 只初始化一次权益、只能领取一次。退货补领中“恢复一次领取资格”应记录独立的重置事件，不作为第二次初始化；它是否允许开启新的领取周期、同一设备允许重置多少次，仍需与一次领取规则对齐。新 SN 初始化和后续领取的确切关系，以正式接口口径为准。

四类状态独立保存、展示：

- **批次处理结果**：本次新增、跳过、重置或失败，是历史事实。
- **激活状态**：是否已经领取 / 激活。是否“领取即激活”需要接口映射确认。
- **当前权益状态**：未生效、有效、已到期、已退权益、待同步等，由权威权益数据决定。
- **订单与真实退款状态**：订单交易进展与资金退款进展分别展示。

批次历史不随当前权益变化而改写。已激活也可能已到期；订单成功不能直接推出权益有效。未提供的字段显示“暂未提供 / 待同步”，不以“无退款”等确定结论代替未知。

## MVP 页面与交互

1. **appkey 入口**：手动输入、验证模拟 appkey，提供可直接使用的示例；切换后清空上一个 appkey 的查询和详情。
2. **SN 权益查询**：支持单 SN 模糊查询与 Excel / CSV 上传批量精确查询；提供示例模板，校验表头、重复、空行及错误行，展示未匹配 SN。按领取状态、权益状态、商品与时间筛选；详情关联订单、真实退款及批次处理记录。
3. **导入批次**：按批次号、文件名、SN、时间及批次状态筛选；展示总条数、新增、跳过、退权益、失败数量。本次模拟已完成批次，正式版再接处理中状态。
4. **批次明细**：按处理结果筛选；逐台展示动作、结果、原因、额度扣减和前后状态，支持导出全部筛选结果。可从 SN 详情反查相关批次。
5. **订单 / 退款查询**：按 SN、订单号、时间及状态筛选，保留第三方订单号、喜马拉雅订单号等追溯字段。

列表提供分页、无结果状态及明确的模拟数据标识。批次各结果数量之和必须等于输入条数；相同 SN 在一个文件出现多行时，每个输入行均应有可追溯的结果。SN 默认保留大小写和前导零，仅去除首尾空格。

## 正式数据与 API 建议

最小模型：客户与 appkey 映射、SN 设备、权益记录、订单、真实退款、导入批次、逐条导入结果，以及资格重置事件。设备使用 `(appkey, SN)` 作为唯一业务键，即应用租户内 SN 唯一；同一个 SN 在不同 appkey 下视作独立设备记录。权益记录保留商品 ID、激活时间、有效期、来源订单和更新时间；重置事件关联原权益、来源批次与额度变动。

建议提供以下只读接口：

- `GET /api/entitlements`：按授权 appkey、SN 和状态分页查询。
- `GET /api/devices/:id`：获取设备的权益、订单、真实退款及处理时间线。
- `GET /api/import-batches`、`GET /api/import-batches/:id/items`：获取批次汇总和逐条结果。
- `GET /api/orders`：查询关联交易及真实退款状态。
- `GET /api/import-batches/:id/export`：按与明细相同的筛选条件导出。

正式接口返回稳定记录 ID、原始业务状态码、处理原因、业务时间、数据更新时间与请求追踪 ID。导出条件、结果统计与明细列表必须保持一致，并统一执行权限校验。

仅有汇总数量的历史接口无法保证恢复逐台明细。应确认已有导入日志是否保存输入与结果；缺失时需要在导入链路新增逐条结果留存，不能通过当前设备状态反推历史。

导入链路应保证白名单新增幂等，并对重置、资格恢复和商品额度扣减建立一致的事务 / 状态机及幂等记录，防止接口重试导致重复退权益或重复扣额度。此能力属于正式后端，不在查询 Demo 中模拟写入。

## 正式鉴权建议

Demo 中输入 appkey 只用于切换模拟数据。正式环境下 appkey 是业务标识，不应作为唯一访问凭证。

可以保留手动输入 appkey 的入口，但服务端还需验证登录会话、客户访问令牌或已签名凭证，并核验它是否有权访问该 appkey。详情、列表、统计、导出均需服务端校验，不能依赖前端过滤。客户与 appkey 采用一对多映射，以兼容同一客户拥有多个 appkey；跨客户访问仅向有相应权限的内部账号开放。

## 上线前待确认

1. **初始化与领取**：初始化是否创建可领取资格？领取与激活是否同一步？权益起止时间如何计算？
2. **重置规则**：“每个 SN 只能领取一次”与“重置后恢复一次领取资格”如何衔接，重置是否开启新领取周期？同一 SN 可否多次退货补领？已到期、处理中或已退权益时能否重置？
3. **商品额度**：额度属于哪个 appkey、活动或商品？每次扣减多少？额度不足与部分处理失败如何回滚？
4. **真实退款字段**：已确认截图的“退款成功”是资金退款；具体有哪些单号、金额、状态与时间字段，以及与退权益的关联方式，仍需确认。
5. **数据与可见字段**：逐台导入结果是否已留存？用户 ID、活动码、分成比例哪些可以向客户展示？
6. **正式访问方式**：采用哪种额外鉴权凭证，客户账号如何绑定 appkey？
